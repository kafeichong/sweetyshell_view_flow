# Video Flow 开发工作流

> 状态：现行工程流程规范。
> 适用范围：产品功能、工作流、接口、数据、计费、安全、自动化和重要文档改造。
> 文档职责：本文规定“如何把一项工作从想法推进到可验证结果”，不描述当前实现，也不安排具体任务。当前事实只看 [PROJECT_STATUS](./PROJECT_STATUS.md)，当前计划只看 [ROADMAP](./ROADMAP.md)。

## 1. 核心原则

1. 功能、目标用户、核心场景或验收结果不明确时，先讨论，不进入实现。
2. 产品语义、权限、费用、数据模型、外部集成和架构边界存在多种合理解释时，必须由 Steven 确认，Agent 不自行选择。
3. 低风险、可逆且不改变产品语义的实现细节，可以由 Agent 作出合理假设，但必须在开始前说明。
4. 计划按可验证的垂直切片拆分。每个切片应产生用户或系统可以观察的完整结果，而不是只完成一层代码。
5. 测试和验证方法先于实现。先说明怎样证明正确，再修改代码。
6. 每完成一个切片立即验证和审查，不把所有问题留到最后集中排查。
7. 测试通过、本地实现、提交、推送、部署、真实环境验收和用户接受是不同状态，必须分别记录。
8. 涉及真实 Provider、生产配置、外部消息、部署或其他有成本/外部影响的动作，必须取得对应范围的明确授权。

## 2. 开始实现前的清晰度判断

收到新功能或改造要求后，先判断需求清晰度。

| 情况 | 处理方式 |
| --- | --- |
| 用户、目标、核心场景、非目标或验收结果不明确 | 先讨论产品意图；不得开始实现 |
| 存在高影响产品、权限、计费、数据、集成或架构选择 | 列出选项、依据和取舍，等待 Steven 确认；必要时记录 ADR |
| 需求明确，但不了解现有代码影响 | 只读探索代码、配置、测试和运行路径，形成影响清单后再计划 |
| 只有低风险实现细节未指定 | 遵循现有结构作最小假设，开始前明确说明假设及验证方式 |
| 线上故障或测试失败 | 先复现、定位原因和影响范围；未授权时不借诊断名义扩大修复范围 |

讨论结论应进入对应权威文档，不能只留在聊天中。尚未达成一致的内容标记为待决策，不得写成已确定需求。

## 3. 十阶段工作流

### 3.1 产品探索

**输入：** 想法、问题、用户反馈或业务目标。

**必须明确：**

- 目标用户；
- 要解决的问题和期望结果；
- 核心使用场景与异常/恢复场景；
- 本期范围和非目标；
- 成本、安全、时间或外部依赖约束。

**出口门禁：** 参与者对“为谁解决什么问题、什么不做”没有实质分歧。产品级稳定结论写入 `docs/PRODUCT.md`；文件尚未建立前，先形成经确认的讨论结论，不直接进入编码。

### 3.2 需求固化

**输入：** 已确认的产品目标与范围。

**必须产出：**

- 可观察的功能行为；
- 用户故事或等价的使用场景；
- 正常、失败、权限不足、恢复等路径；
- 可证伪的验收标准；
- 明确非目标和兼容边界。

**出口门禁：** 每项需求都能回答“输入什么、发生什么、用户看到什么、如何证明”。工作流需求必须遵守 [Preview 与 Production 统一需求规范 v2](./requirements/2026-09-15/workflow-preview-production-spec-v2.md)。

### 3.3 代码库探索

**输入：** 已确认需求。

**必须检查：**

- 实际入口、调用链和数据流；
- 可复用模块与现有测试；
- 数据库、配置、迁移、部署和外部依赖；
- 鉴权、费用、幂等、恢复和兼容风险；
- 当前工作区未提交修改，避免覆盖无关工作。

**出口门禁：** 形成具体到文件和接口的影响清单，区分可保留能力、需要替换的行为和不在本次范围的风险。分析结论以当前源码和运行证据为准。

### 3.4 技术决策

**输入：** 需求和代码影响清单。

**必须处理：** 模块职责、接口合同、数据模型、状态语义、错误处理、迁移/回滚和兼容策略。

以下情况必须先讨论并记录 ADR：

- 改变跨包或对外接口；
- 改变数据库核心模型或不可逆迁移策略；
- 改变权限、费用、幂等或恢复语义；
- 引入新的外部服务或长期依赖；
- 存在两个以上各有明显取舍的长期方案。

**出口门禁：** 高影响选择已有明确决定和理由；实现者不需要在编码时重新猜测产品或架构含义。

### 3.5 实现计划

**输入：** 冻结的需求和必要技术决策。

计划按垂直切片拆分，每个切片写明：

- 用户或系统可观察结果；
- 修改和新增文件；
- 输入、输出和依赖；
- 失败测试或复现方式；
- 目标验证、集成验证和真实验收边界；
- 安全、费用、迁移和回滚要求。

**出口门禁：** 每个任务可以独立实现、验证和审查。具体任务与顺序只写入 [ROADMAP](./ROADMAP.md)。

### 3.6 测试或验证方法先行

**输入：** 一个可独立交付的切片。

实现前必须说明：

- 哪个测试或复现当前会失败；
- 正确实现后应观察到什么；
- 哪些副作用必须保持为零；
- 哪些场景需要单元、合同、HTTP、数据库、ComfyUI 或真实 Provider 验证；
- 哪些验证受环境或授权限制，不能在本轮冒充完成。

**出口门禁：** 验证方法能够区分“代码存在”和“功能正确”，并覆盖主要失败路径。

### 3.7 Agent 分步实现

每个切片依次执行：

```text
确认范围和工作区
→ 写失败测试或稳定复现
→ 确认失败原因符合预期
→ 最小必要实现
→ 运行目标测试
→ 检查差异和无关修改
→ 更新必要文档
```

共享合同应有单一负责人。可以并行进行只读证据核对或互不重叠的模块实现，但不得让多个 Agent 同时自行定义同一 DTO、Registry、计费规则或 Provider payload 语义。

**出口门禁：** 当前切片目标测试通过，变更范围可解释，没有夹带无关重构；未通过时继续定位，不进入下一切片。

### 3.8 独立代码审查

审查人与实现者的关注点分离。审查至少覆盖：

- 业务行为和验收标准；
- 架构边界与重复规则；
- 鉴权、越权、密钥和敏感信息；
- 预算、计费、幂等和重复 Provider 调用；
- 失败、恢复、交付和回滚；
- 测试是否覆盖真实入口，是否为错误旧行为保绿；
- 数据库 migration 与兼容性；
- 无关修改、临时产物和文档同步。

审查发现应包含文件/位置、影响、建议和验证方法。高风险问题未关闭前不得进入发布门禁。

### 3.9 集成验证

按变更风险选择并记录验证层级：

1. 目标单元测试；
2. 对应包完整测试、build 和可用的静态检查；
3. 合同资源同步与跨包合同；
4. 真实 Controller/Guard、数据库和 Fake Provider；
5. 实际 ComfyUI 安装、导入、执行和恢复；
6. 经单独授权的真实 Provider、产物、usage 和费用验收。

工作流和关键链路变更至少执行仓库要求的三包回归；涉及执行、计费或恢复时必须补跨包合同。真实环境未执行时必须明确写“未验证”，不能由单测或 Fake Provider 结果替代。

### 3.10 经验沉淀

完成切片后，根据变更性质更新：

| 变化 | 更新位置 |
| --- | --- |
| 产品用户、目标、核心场景、范围或非目标变化 | `docs/PRODUCT.md` |
| 强制功能行为或验收标准变化 | `docs/requirements/` |
| 长期架构取舍或核心语义变化 | `docs/architecture/` 下的 ADR |
| 任务、顺序、阶段出口变化 | `docs/ROADMAP.md` |
| 当前能力、缺口、风险和验证结果变化 | `docs/PROJECT_STATUS.md` |
| 操作、部署、恢复或排障步骤变化 | `docs/runbooks/` |
| 所有贡献者或 Agent 都必须遵守的仓库规则变化 | `AGENTS.md` |
| 跨项目可复用、经过验证且需要稳定自动执行的方法 | Skill |

一次性实现细节不写入 `AGENTS.md` 或 Skill。尚未验证的经验先记录为观察或风险，不能提升为强制规则。

## 4. Definition of Ready

任务进入实现前必须满足：

- [ ] 用户、问题、目标结果和非目标明确；
- [ ] 需求不存在会改变结果的未决歧义；
- [ ] 正常、失败、权限和恢复路径有验收标准；
- [ ] 已检查实际代码入口、依赖、现有测试和未提交修改；
- [ ] 高影响技术决策已确认，必要 ADR 已记录；
- [ ] 已拆成可独立验证的垂直切片；
- [ ] 已定义失败测试、验证命令和副作用边界；
- [ ] 付费、部署或外部操作所需授权范围明确。

任一项不满足时，继续讨论、调研或补充计划，不进入实现。

## 5. Definition of Done

任务只能在以下事实分别记录后判断完成程度：

- [ ] 需求范围内的实现已经完成；
- [ ] 目标测试通过；
- [ ] 独立代码审查完成，高风险问题已关闭；
- [ ] 适用的包级、跨包和故障路径验证通过；
- [ ] migration、配置、runbook 和文档已同步；
- [ ] 未完成项、skip、环境限制和风险已经列明；
- [ ] 本地、提交、推送、部署、真实环境和用户验收状态分别记录；
- [ ] 涉及付费 Provider 时，实际任务、费用和产物证据没有被测试结果替代。

“代码已写”“测试全绿”“已经部署”都不能单独代表功能完成。单个工作流的完成定义仍以 v2 规范和对应验收标准为准。

## 6. 标准交接记录

每个切片完成或暂停时，至少记录：

```text
目标：
已完成：
修改文件：
验证命令与结果：
独立审查结论：
未验证范围：
风险与回滚：
提交 / 推送 / 部署 / 真实验收状态：
下一步：
```

材料较多时，当前事实归并到 `PROJECT_STATUS.md`，后续任务归并到 `ROADMAP.md`；固定日期的完整评审或决策证据可以归档，但不得复制并长期维护另一套现状或计划。
