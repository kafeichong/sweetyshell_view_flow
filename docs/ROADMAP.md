# Video Flow 项目路线图（权威）

> 最后更新：2026-09-11
> 本文是**唯一**描述"接下来做什么、什么时候做、怎么验收"的文档。
> 现状与风险编号（R1、R2…）见 [PROJECT_STATUS.md](./PROJECT_STATUS.md)。

---

## 1. 规划原则

1. **资金安全优先于功能速度。** 任何"能让 Worker 真实花钱"的路径，必须先有鉴权 + 额度两道闸门。
2. **一个阶段只开放一类用户。** Preview → 单人 Production → 小组 Production → 全员，每级都要过门禁。
3. **每个阶段都有可证伪的验收标准。** 不做"差不多能用了"的判断；门禁未过不进下一阶段。
4. **不追求功能广度。** 本期唯一成功标准：创意同事能安全、可追溯、成本可控地自己出片。
5. **测试全绿不构成验收。** 关键路径必须有端到端契约验证。

---

## 2. 成功标准（整体目标）

同时满足以下四条，才算这套系统真正可用：

- **核心链路稳定**：素材上传 → 创建任务 → Provider 生成 → OSS 归档 → 同事取回成片，全程可自助。
- **追溯能力完整**：任意一条历史成片都能回答：谁、什么设备、什么 Workflow、哪个模型、什么 Prompt、什么输入素材、什么参数、花了多少钱。
- **成本可控**：有额度闸门，超限被拒；月度 usage 与火山账单可对账。
- **资金风险受控**：无未授权付费路径，无重复计费。

## 3. 阶段规划

### Phase 0：安全封口与基线固化（1 周）

**目标：把公网可付费面清零，让仓库回到干净可回归的状态。**

#### 2026-09-11 执行计划

本轮直接在当前工作区实施，不创建额外 worktree；现有文档重组与代码修复精确分批暂存，禁止使用 `git add -A`。Production 白名单全程保持为空，不运行任何会创建 Provider Task 的验收。

1. **旧接口封口**：为旧 `/api/tasks` 的 `POST /`、`GET /`、`GET /pending`、`GET /:id` 加 `AdminTokenGuard`；`claim`、`recover`、`PATCH /:id` 继续使用 `WorkerServiceGuard`。先写真实 decorator metadata 测试，再实现；部署后用无 body 的 POST 和 GET 验证 401，避免测试失败时意外创建付费任务。
2. **端口收敛**：Backend 只发布 `127.0.0.1:3100:3000`；Worker 和 PostgreSQL 删除宿主 `ports`，仅保留 Docker 网络。部署前备份数据库并记录 Compose 配置，部署后验证 Nginx HTTPS、容器内互通以及宿主无 `0.0.0.0:3100/8101/5433`。
3. **凭证卫生**：确认 `.env.backup-token-*` 仅为历史临时备份后删除，生产 `.env` 权限设为 `600`；全程不输出文件内容。删除前记录文件名、权限和修改时间。
4. **三包 CI 与客户端测试入口**：增加 GitHub Actions，运行 Backend `build + jest`、Worker `pytest`、Client `pytest`；用客户端 `conftest.py` 固定源码导入路径，使测试从仓库根和包根运行均通过。
5. **文档基线**：保留当前 `docs/` 重组，更新 `PROJECT_STATUS.md`、本文件和相关 runbook 中已完成风险与新命令；单独提交文档，不与代码、部署配置混在一个 commit。
6. **创意人员交付**：提供客户端安装脚本、管理员 credential 签发/撤销脚本与不含密钥的交付说明；在第二台真实 ComfyUI 电脑完成 Preview 验收后才允许发放。该验收必须满足 `status=preview`、Attempt=0、Production=403、无 Provider Task ID/费用。

执行顺序固定为 `1 → 2 → 3 → 4 → 5 → 6`。任一安全门禁失败立即停止后续交付；代码/配置修改、本地验证、提交推送、生产部署和第二台电脑验收分别记录，不互相替代。

### Phase 1：单人 Production 灰度（1–2 周）

**目标：让 1 位创意同事在零研发协助下，安全完成真实付费出片，且成本可控、可追溯。**

| 任务 | 对应风险 | 估时 |
| --- | --- | --- |
| 额度闸门：单次上限 + 日 / 月额度校验，超限返回 429 并说明提额路径；被拒请求不创建 ExecutionAttempt | R3 | 1 天 |
| 产物交付闭环：输出 Asset 补 `ownerId` + `inspectionStatus='uploaded'`；`videoUrl` 改存 `objectKey`，签名按需生成 | R4 | 1 天 |
| 客户端补齐：Production 提交节点 + 结果加载节点（直接把视频写进 ComfyUI output） | R7 | 1.5 天 |
| 重试与恢复：补 retry 迁移 + 仅对"确认未提交成功"的失败做有限自动重试（≤2 次、退避）；`requires_review` 有明确人工处置路径 | R6 | 1.5 天 |
| 恢复验收：杀 Worker 重启，验证已提交任务恢复轮询且**不产生第二次计费** | R13 | 0.5 天 |
| 幂等键纳入生成参数（profile / duration / ratio） | R12 | 0.5 天 |
| 上线检查表与回滚演练（用 [runbooks/deploy-and-rollback.md](./runbooks/deploy-and-rollback.md) 补全执行人与时间） | — | 0.5 天 |
| 真实出片 3 条，逐条记录 usage 与推算费用，并与火山账单核对一次 | R11 | 0.5 天 |

**出口门禁：**

- [ ] 1 位非研发同事独立完成 3 条不同 prompt 的真实出片，全程无研发介入。
- [ ] Worker 重启实验：0 次重复计费、0 次重复 Provider 提交。
- [ ] 超额请求 100% 被拒，且不产生 ExecutionAttempt。
- [ ] 出片视频可在 ComfyUI 内直接查看，不依赖 7 天签名 URL。
- [ ] 每条任务可追溯到 actor、设备、Workflow、Provider、Attempt、usage、费用状态。
- [ ] 本次灰度费用完成一次账单核对，偏差有书面结论。

**目标：从"1 个人能用"变成"一个小组敢用"——有额度、有告警、有对账、有审核、有后台。**

**出口门禁：**

- [ ] 5–10 人稳定使用两周，无非预期额度超支。
- [ ] 任务成功率 ≥ 95%；失败任务 100% 有 `failureType` 归因。
- [ ] MTTR < 30 分钟，且有告警在用户投诉前触发。
- [ ] 月度账单偏差 < 5%，或偏差有书面解释。

### Phase 3：平台化（可选，Month 2 之后）

仅在 Phase 2 门禁稳定通过、且出现明确业务需求时启动：

- 多 Provider 抽象与路由（Worker 现有 adapter 结构已预留）。
- 成本优化：分辨率 / 时长档位、内容寻址复用、失败前拦截。
- Workflow 版本管理与参数模板，沉淀"可复用的出片配方"。
- 同一后端支撑更多创意链路（图生图、配音、剪辑拼接），避免每条链路重造鉴权与账务。
- 容量与 SLA 规划；Worker 持久队列与水平扩容。

## 7. 明确不做（Out of Scope）

- 服务器集中部署 ComfyUI 或 Seedance 模型（架构基线已冻结此边界）。
- 把 Ark / OSS 密钥下发到任何同事电脑。
- Phase 0 门禁未通过前，把 Production 开放给第二个人。
- 多 Provider 接入、成本优化、完整管理后台 UI（属 Phase 3，避免范围蔓延）。
- 为验证而创建无业务意义的付费任务（沿用零付费验收原则）。
