# 接入 Seedance 2.0 的评估

> 日期：2026-09-18
> 用途：评估"在现有 Seedance 2.5 之外再接入 Seedance 2.0"的改动面、风险与验收成本。
> **本文不是当前系统状态**：现状以 [PROJECT_STATUS.md](../PROJECT_STATUS.md) 为准。
> **本文不构成任何授权**：文末的待决策项未定之前，不得据此开工。

## 0. 结论摘要

**这不是"接第二个接口"，而是"把单模型系统改成多模型系统"。**

三个理由：

1. **合同里"模型"是单数的**，而且被深度引用（报价取 `model.dimensions`、Worker 校验 `model.id`）。
2. **`model.id` 在执行摘要（execution digest）里**——"让用户能选模型"等于改执行规则，会让所有在途任务的冻结快照失配。这是本评估最大的技术风险，且**躲不过**（加素材库时靠"顶层 `media` 不参与 digest"绕开了，这次没有等价的位置）。
3. **两个模型的能力表不一样**，其中一条直接卡死我们现有工作流（见 §3）。

**粗估**：设计 1–2 天 → 实现 3–5 天 → 真实验收 2–3 天。**最大的成本不是代码，是验收**——R8 那套真实验收要按"工作流 × 模型"重跑。

## 2. 现状：单模型假设嵌在哪里

### 2.1 合同结构（单数）

```jsonc
"model": {
  "key": "seedance-2.5", "id": "doubao-seedance-2-5-260628",
  "createTaskPath": "/api/v3/contents/generations/tasks",
  "outputFrameRate": 24,
  "resolutions": ["480p","720p","1080p"],
  "ratios": [...], "outputFormats": ["mp4","mov"],
  "dimensions": { "480p": {...}, "720p": {...}, "1080p": {...} }
}
```

**没有放第二个模型的位置。** 代码里到处是 `contract.model.X`：

| 位置 | 用途 |
| --- | --- |
| `packages/backend/src/tasks/task-quote.service.ts:25,37,132` | 报价按 `model.dimensions[resolution][ratio]` 取像素 |
| 同上 `:145` | 帧率取 `model.outputFrameRate` |
| `packages/worker/providers/seedance_execution_policy.py:57` | **硬校验** `params.model === _CONTRACT.model.id`，否则拒绝 |
| 同上 `:142` | 构造 payload 时写死 `model` 字段 |

### 2.2 执行摘要包含 `model.id`（关键）

```ts
// packages/backend/src/tasks/workflow-catalog.service.ts
workflowExecutionDigest = digest({
  schemaVersion, provider,
  model: { id: value.model.id },      // ← 在这里
  workflows: [{ key, capability, media, generation, providerFields }],
});
```

Worker 侧同构（`seedance_execution_policy.py:13-34`），且 `_validate_frozen_contract`（`:53-65`）**只比对、不做向后兼容**。失配的后果与"新增 workflow key"完全相同：在途任务编译失败 → `requires_review` → **无自动恢复路径**。

### 2.3 定价没有模型维度

```jsonc
"pricing": { "catalogRates": [
  { "resolutionGroup": "480p_or_720p", "hasInputVideo": false, "cnyPerMillionTokens": "70.00" },
  { "resolutionGroup": "480p_or_720p", "hasInputVideo": true,  "cnyPerMillionTokens": "42.00" },
  { "resolutionGroup": "1080p",        "hasInputVideo": false, "cnyPerMillionTokens": "77.00" },
  { "resolutionGroup": "1080p",        "hasInputVideo": true,  "cnyPerMillionTokens": "46.00" }
]}
```

分档键是「分辨率组 + 是否含输入视频」，**没有"哪个模型"这一维**。

### 2.4 硬编码散落 55 处

`grep -rn "doubao-seedance-2-5-260628"`：**55 处，分布在 24 个文件**（合同 11 处、代码与测试 44 处）。

## 3. 两个模型的实际差异（决定可行性）

| 维度 | **Seedance 2.5**（现用） | **Seedance 2.0** |
| --- | --- | --- |
| 最高分辨率 | 1080p | **4K（3840×2160）** |
| 1080p 位深 | **10bit** | 8bit |
| 4K 位深 | 不支持 | 10bit |
| **输出时长** | **4~30 秒** | **4~15 秒** |
| **输出格式** | **mp4, mov** | **仅 mp4** |
| **纯音频参考** | ✅ 可独立使用 | ❌ **必须搭配图片/视频** |
| 480p/720p 单价 | 70 元/百万 | **46 元/百万** |
| 1080p 单价 | 77 元/百万 | 51 元/百万 |
| 4K 单价 | — | 26 元/百万（含输入视频 16） |
| 参考素材上限 | 50（30 图 + 10 视频 + 10 音频） | 15（9 图 + 3 视频 + 3 音频） |

### 3.1 会卡死现有工作流的三条

1. **视频编辑与视频延长固定输出 `mov`** → **2.0 上跑不了**（它只出 mp4）。除非把这两条改成 mp4，但 `mov` 是当初照官方范例定的。
2. **时长上限 15 秒** → 合同里的 16–30 秒档在 2.0 上非法。客户端时长下拉（4–30）要按模型联动。
3. **纯音频参考** → 2.0 上必须搭配图片/视频，而我们的 `seedance.audio-reference-to-video.v1` 是**纯音频**入口。

## 4. 工作量拆解

| # | 工作项 | 量级 | 说明 |
| --- | --- | --- | --- |
| 1 | 合同结构改造 | 中 | `model` 单对象 → 多模型。**先要设计决策**：并列数组 `models[]`？还是 `model.alternates[]`？ |
| 2 | **digest 兼容** | **大** | 见 §5.1。双 digest 并行窗口，或等冻结期 |
| 3 | 定价加模型维度 | 中 | `catalogRates` 增加模型键；促销与账号价的键同步 |
| 4 | 能力差异校验 | 中 | 分辨率档、时长上限、输出格式、音频参考限制**按模型分别判** |
| 5 | Worker 编译器 | 小 | 模型校验从"等于唯一 id"改为"在允许集合内"；payload 的 model 字段 |
| 6 | 客户端 | **中偏大** | 模型选择 UI、参数联动（选 4k 自动锁 2.0；选 2.0 则时长上限 15、格式锁 mp4）、模板 |
| 7 | 测试 | 中 | 55 处引用 + 合同不变量 + 序列化 |
| 8 | **真实验收** | **大** | 2.0 从未在真实账号上跑过；8 类工作流 × 2 模型都要重跑 |
| 9 | 素材库兼容 | 待验证 | `asset://` 在 2.0 上是否可用**没有依据**（我们全部验证都是 2.5） |

## 5. 风险

### 5.1 digest 变更（最高风险）

"模型可选"是**执行规则**。按本项目的既定规矩（改 `generation.productDuration` 就必须改 digest），它**理应**让 digest 变化——而 Worker 对已冻结快照是**零兼容**的。

两条出路，都要单独安排：

- **双 digest 窗口**：Worker 同时接受 N 与 N-1 两版摘要并各自编译，保留到旧任务排空。这是一块独立工程，不能混进"接 2.0"里顺带做。
- **冻结期**：挑一个没有在途任务的窗口切换（生产当前在途为 0，但这是偶然状态，不是保证）。

### 5.2 能力矩阵的分叉会持续存在

两个模型在**时长、格式、音频参考、分辨率**四个维度都不同，且 2.0 还有 fast/mini 两个变体（只支持 480p/720p）。合同的 `workflows[].generation` 目前描述"这条工作流能做什么"，一旦多模型，它要变成"**这条工作流在每个模型上分别能做什么**"——表达力和校验复杂度都会上一个台阶。

### 5.3 验收成本是主导项

R8 的验收记录（`validation.records`）绑定的是**具体模型**。接了 2.0 之后：

- 每条工作流在 2.0 上要**重新出一遍片**才算验证过
- 而 §3.1 那三条（编辑 / 延长 / 纯音频）在 2.0 上**根本跑不了**，对应的工作流只能对 2.5 开放

### 5.4 其它

- 2.0 的 1080p 是 8bit，2.5 是 10bit —— 同一个"1080p"档，画质不同，创意同事会困惑。
- 2.0 的 4K 只在 `16:9` 有尺寸（官方表里其它比例为 `—`），比例支持面比 2.5 窄。

## 6. 待决策的问题

**先答这三个，再谈实现。**

| # | 问题 | 为什么必须先答 |
| --- | --- | --- |
| Q1 | **要的是 4K，还是更便宜？** | 4K 只能走 2.0；而"便宜"是定价/成本问题，与接入是两件事 |
| Q2 | **要不要"用户可选模型"，还是"服务端按规则选"？** | 前者要动客户端与 digest；后者可以把范围压到"仅 4K 档走 2.0" |
| Q3 | **视频编辑 / 延长在 2.0 上要不要放弃 mov？** | 若要，那两条工作流在 2.0 上直接不可用；若改 mp4，要重新验收 |

## 7. 建议路径（取决于 Q1/Q2）

**若只要 4K（范围最窄）**

```
只在 4k 这一档走 2.0，其余参数仍走 2.5
  → 合同加"分辨率 → 模型"的映射，而非全面多模型化
  → 客户端在选 4k 时提示"将使用 Seedance 2.0（输出 mp4、时长上限 15 秒）"
  → 仍要过 digest、定价、验收三关，但改动面显著小于全面多模型
```

**若要"用户可选模型"（范围最大）**

```
合同 model → models[]，workflows[].generation 按模型分叉
  → 必须先做双 digest 窗口
  → 客户端模型选择 + 参数联动
  → 验收按 工作流 × 模型 重跑
```

**无论走哪条**：先做一次**真实账号的 2.0 冒烟**（一条 4K 或一条 480p，最便宜的那档），确认：
- 2.0 的接口形状与 2.5 是否一致（`content`、`role`、`ratio`、`duration` 语义）
- `asset://` 在 2.0 上是否可用
- 4K 的实际出片尺寸与 `16:9` 之外的请求行为

这一步很便宜（几元），但能把 §4 里"待验证"的那一格先钉死。
