• 现在代码里的实际逻辑，可以按下面这条链理解：

  ComfyUI
    │
    ├─ Preview：只检查请求结构和素材元信息
    │                    不上传素材、不创建付费任务、不调用 Ark
    │
    └─ Production：
         1. 必须是 production_verified 工作流
         2. 必须有有效 preflightId + confirmLiveSubmission=true
         3. 必须上传素材并登记 Asset
         4. 服务端校验 Asset 归属、角色、MIME、实际文件 SHA-256
         5. 按本次 duration/ratio/resolution 计算预占金额
         6. 创建 pending Task 和预算预占
         7. Worker claim 后调用 Ark 正式接口
         8. Ark 返回 completion_tokens 后结算

  ### 1. 现在有哪些工作流状态

  当前 Registry 里有三种状态：

   状态                            Preview    Production
  ━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━
   production_verified                可以          可以
  ─────────────────────  ──────────────────  ────────────
   preview_only                       可以          拒绝
  ─────────────────────  ──────────────────  ────────────
   disabled               可以进入 Preview          拒绝

  目前只有：

  seedance.reference-image-to-video.v1

  是 production_verified。

  所以现在实际可走正式接口的路径是：

  参考图 → 4–30 秒 → 标准比例 → 480p/720p/1080p → Ark Production

  文本生视频、首帧、首尾帧、多参考、视频编辑、视频延长、音频参考等工作流目前只能 Preview，不能
  Production。

  这里需要特别说明：disabled 可以进入 Preview，是当前代码行为；docs/PROJECT_STATUS.md 里仍有旧文
  字写成“disabled 无法创建 Preview”，那部分文档已经过时，应该更新。

  ### 2. Preview 到底做什么

  普通 Preview 请求：

  POST /api/v1/tasks
  {
    "mode": "preview",
    "workflowKey": "...",
    "generation": {
      "duration": 10,
      "ratio": "16:9",
      "resolution": "720p"
    },
    "media": [...]
  }

  Preview 只做：

  - 检查 workflowKey
  - 检查工作流允许的媒体角色、数量和顺序
  - 检查 duration
  - 检查比例和分辨率
  - 返回规范化后的请求
  - 保存一个不可执行的 Preview Task

  Preview 不做：

  - 不上传素材
  - 不调用 Ark
  - 不创建 pending 正式任务
  - 不创建 ExecutionAttempt
  - 不预占预算
  - 不产生 Provider Task ID

  因此，Preview 通过不能代表“已经生成过视频”，也不能代表“正式接口一定接受”。

  ### 3. Production 的正式准入条件

  Production 请求必须同时满足：

  生产 Actor
  + production_verified 工作流
  + 有效的 preflightId
  + confirmLiveSubmission=true
  + 素材属于当前 Actor
  + 素材已上传
  + Asset 角色与工作流匹配
  + MIME 与实际媒体类型匹配
  + 实际对象内容 SHA-256 校验通过
  + 预算检查通过
  + 幂等键有效

  Production 仍然会再次对请求做服务端校验，不信任客户端的：

  confirmed=true
  sha256=...
  isValid=true

  这也是为什么“Preview 允许”不等于“Production 允许”。

  ### 4. 4–30 秒现在是怎么生效的

  对于当前正式开放的参考图工作流，Registry 允许：

  duration: 4–30
  ratio: 21:9 / 16:9 / 4:3 / 1:1 / 3:4 / 9:16
  resolution: 480p / 720p / 1080p

  Production 不再强制把请求改成 VIDEO_FLOW_PRODUCTION_SPEC_JSON 里的固定 5 秒或固定 720p。

  VIDEO_FLOW_PRODUCTION_SPEC_JSON 当前主要提供：

  - 正式模型
  - pricingVersion
  - generateAudio
  - watermark
  - 生产规格版本
  - 兼容用的 reserveCny

  真正的请求参数来自本次请求：

  normalized.generation.duration
  normalized.generation.ratio
  normalized.generation.resolution

  所以 30 秒 Production 请求会继续以：

  {
    "duration": 30,
    "ratio": "16:9",
    "resolution": "1080p"
  }

  传到执行计划，再由 Worker 编译给正式 Ark 接口。

  Worker 对 Seedance 2.5 的时长校验也是：

  4 <= duration <= 30

  正式接口调用地址是：

  {VIDEO_FLOW_PROVIDER_BASE_URL}/contents/generations/tasks

  也就是说，目标链路不是本地 ComfyUI 生成，而是：

  Backend 创建正式 pending Task
  → Worker claim
  → Worker 编译 Ark payload
  → Worker 调用 Ark 正式 generations/tasks 接口

  ### 5. 预占金额现在怎么计算

  官方页面给出的估算公式是：

  token 用量 =
  (输入视频时长 + 输出视频时长)
  × 输出视频宽
  × 输出视频高
  × 输出视频帧率
  / 1024

  费用是：

  预估费用 = token 用量 × 每百万 token 单价

  当前代码对 Seedance 2.5 官方价格版本使用：

   输出分辨率          不含输入视频
  ━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━
   480p          70 元 / 百万 Token
  ────────────  ────────────────────
   720p          70 元 / 百万 Token
  ────────────  ────────────────────
   1080p         77 元 / 百万 Token

  当前估算默认按 24 FPS，并根据分辨率和比例计算输出宽高。

  例如：

  30 秒
  16:9
  1080p
  无输入视频，只有参考图

  估算结果是：

  estimatedTokens = 1,458,000
  estimatedCost = 112.266000 元

  计算过程相当于：

  30 × 1920 × 1080 × 24 / 1024
  = 1,458,000 tokens

  1,458,000 / 1,000,000 × 77
  = 112.266 元

  官方也明确说明，估算值不是最终准确用量，最终要以 API 返回的：

  usage.completion_tokens

  为准。费用和 Token 公式以火山方舟官方模型价格页为准。

  ### 6. 实际结算怎么做

  当前 Backend 的正式价格版本：

  seedance-2-5-official-v1

  只接受：

  usage.completion_tokens

  然后根据正式执行计划中的：

  pricingVersion
  model
  resolution
  media

  计算实际费用。

  历史版本：

  seedance-token-v1

  仍兼容旧的：

  usage.total_tokens

  这样做是为了防止旧任务因为字段变化无法恢复，同时避免新任务错误地拿 total_tokens 结算。

  ### 8. 目前还存在的两个逻辑问题

  这两个需要继续修，否则“预检显示的金额”和“正式提交检查的金额”并不完全一致。

  #### 问题一：checkPreflight 还在使用固定 reserveCny

  当前正式预检提交时，会使用实际参数计算：

  estimateSeedanceCost(...)

  但是：

  GET /api/v1/tasks/preflight/:id/check

  目前仍然使用：

  spec.reserveCny

  做预算检查。

  也就是说：

  预检创建：可能显示 112.266 元
  预检检查：却可能按 VIDEO_FLOW_PRODUCTION_SPEC_JSON 的固定金额检查
  正式创建：再按 112.266 元预占

  这会造成三个阶段的金额判断不一致。

  应该统一成：

  preflight 创建
  → preflight check
  → Production 创建

  全部使用同一个官方参数估算函数

  #### 问题二：Worker 的 calculate_actual_cost 仍然是旧的固定 70 元

  Backend 结算已经根据分辨率区分：

  480p/720p: 70
  1080p: 77

  但 Worker 的旧辅助方法仍然固定：

  completion_tokens / 1,000,000 × 70

  目前正式台账的主要结算依据是 Backend 返回的 usage 解释结果，所以不会直接导致正式预占金额错误；
  但 Worker 自己记录的 actual_cost 可能和 Backend 的结算不一致，尤其是 1080p 或输入视频场景。

  这个方法也应该改成读取执行计划里的：

  pricingVersion
  resolution
  media 是否包含 reference_video

  不要继续固定使用 70。
