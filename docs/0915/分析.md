  ### 1. 旧 Preview 仍然上传素材，是明确违反规则的行为

  旧节点先把图片编码，然后执行：

  uploaded = client.upload_media(...)

  随后才创建 Preview 请求。这个节点仍在 NODE_CLASS_MAPPINGS 中注册，新节点的加入没有替换它。

  因此，之前说“Preview 都不上传素材”不准确，只适用于新的预检节点链。

  证据：旧 Preview 上传逻辑 (packages/comfyui-video-flow-client/nodes.py:81)、仍注册旧节点
  (packages/comfyui-video-flow-client/nodes.py:304)。

  ### 2. Preview 仍然被生产权限直接卡住

  本地使用测试替身复现：

  有效身份，但没有生产白名单权限
  → 403，不能获得预检报告

  Production 暂停
  → 400 PRODUCTION_PAUSED，不能获得预检报告

  按照我们的定义，这两种情况应当允许完成请求检查，在报告中明确“暂不可正式提交”。

  另外，对于被禁用的首帧工作流，预检报告仍显示参数通过，checkPreflight 还能返回 valid=true；直到正
  式创建任务才拒绝。后端最终拦截仍然有效，但报告没有提前把原因讲清楚。

  证据：预检与提交前检查 (packages/backend/src/v1/tasks/v1-tasks.controller.ts:65)。

  ### 3. Preview 会接受角色与类型不匹配的素材

  我构造了下面这份元信息：

  工作流：参考图片生视频
  素材角色：reference_image
  实际声明类型：audio/mpeg
  元信息：audio，5 秒

  调用当前预检函数，结果被接受。

  原因是：

  - 媒体检查验证了“它是一份合法的音频元信息”。
  - Registry 验证了“reference_image 是这个工作流允许的角色”。
  - Preview 没有把这两个判断关联起来。

  Production 有额外检查，会拒绝这种不匹配；但 Preview 的“参数检查通过”是不完整的。

  证据：Preview 素材检查 (packages/backend/src/v1/tasks/workflow-preflight.ts:23)、Production 角色
  与类型检查 (packages/backend/src/tasks/workflow-registry.ts:161)。

  ### 实际媒体识别还不够独立

  当前媒体检查器在看到视频流后，如果传入的预期 MIME 是 image/*，就返回 kind: image。

  我给检查器注入了带有 H.264 视频流、5 秒时长的 MP4 探测结果，同时传入 image/png，它仍返回：

  kind: image
  width: 500
  height: 500

  这是检查器逻辑的本地复现，说明“实际字节哈希正确”与“媒体类型真正正确”还没有完全闭合。

  证据：媒体类型判断 (packages/backend/src/assets/media-inspector.service.ts:31)。

  ### 恢复已有任务仍可能被预检卡住

  新画布的执行顺序是：

  RequestPreview 检查预检有效期、当前权限与预算
  → CreateTask 查询已有任务回执
  → 等待或下载

  这意味着已有任务生成成功后，如果预检过期，或者额度已经被该任务消耗，重新运行画布可能先失败，根本
  到不了“找回原任务”。

  底层没有因此自动重复生成，但“继续等待、重新下载原产物”的用户流程不完整。

  证据：先检查预检有效期 (packages/comfyui-video-flow-client/preflight_nodes.py:255)、之后才查询任
  务回执 (packages/comfyui-video-flow-client/preflight_nodes.py:290)。
