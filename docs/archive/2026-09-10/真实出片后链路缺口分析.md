# 真实出片后链路缺口分析

> 日期：2026-09-10
> 范围：Seedance 图生视频 Production 链路、ExecutionAttempt 追溯、Asset 上传状态、历史文件哈希与费用口径
> 文档性质：现状分析与修复排期建议，不代表代码已修改、提交或部署

## 一、结论摘要

本次真实出片已经证明“真实图生视频主链路可用”，但还不能等同于“生产级闭环完成”。

已验证通过的主链路为：

```text
ComfyUI 本地图片
  -> Backend 申请上传票据
  -> 图片直传 OSS
  -> 创建 Production Task
  -> Worker 原子 claim
  -> 解析 image_asset_id
  -> Seedance Provider 创建任务
  -> Provider 轮询完成
  -> 下载 MP4
  -> 上传 OSS
  -> 回写任务状态、产物与 usage 推算费用
```

当前剩余问题分为三类：

1. `ExecutionAttempt` 的模型与时间链没有完整写入，既影响审计，也会影响恢复超时判断。
2. 输入素材没有“上传完成确认”，数据库无法可靠区分“只签发了票据”和“OSS 对象已存在”。
3. 旧输入素材没有完整回填 `file_hash`，历史去重和追溯能力不完整。

此外，在分析中确认了一个相关并发缺口：当前 `(owner_id, role, file_hash)` 没有数据库唯一约束，并发上传相同文件时仍可能产生重复 Asset。

## 三、已经解决的三个关键问题

### 3.1 Preview 误触发付费调用

历史问题是服务端忽略 `mode`，`/api/tasks/claim` 又默认按 Production 领取，因此在 ComfyUI 中点击 Preview 也可能进入真实 Provider 调用。

当前处理方式：

- 缺省 `mode` 按 `preview` 处理。
- Preview Task 以 `status='preview'` 落库。
- Worker claim 只领取 `status='pending'`。
- Production 只对白名单 actor 开放。
- Production 白名单为空时，对所有 actor 返回 `403`。

相关实现：

- `packages/backend/src/v1/tasks/v1-tasks.controller.ts`
- `packages/backend/src/v1/tasks/preview-plan.ts`
- `packages/backend/src/v1/tasks/production-policy.ts`
- `packages/backend/src/tasks/tasks.service.ts`
- `packages/backend/src/tasks/task-claim.service.ts`

该设计的关键价值是：Preview 不只是客户端约定不付费，而是在数据库状态和 Worker claim 条件上结构性不可执行。

### 3.2 相同工作流重复提交必然 409

客户端幂等键由 `prompt + 图片内容` 计算，因此相同输入的幂等键是稳定的；但原请求体中的 `asset_id` 每次上传都会变化，导致服务端判断为“相同幂等键、不同请求体”，返回 `409`。

当前处理方式：

- 客户端计算图片 SHA-256。
- 上传票据请求携带 `sha256`。
- Backend 按同一 owner 的 `file_hash` 查找已有输入 Asset。
- 相同内容复用原 `asset_id` 和 `object_key`。

已经实测连续执行两次得到相同的 `asset_id` 和 `task_id`。

### 3.3 ComfyUI 无法获得进程环境变量中的 token

`launchctl` 和 `osascript` 注入环境变量均被系统权限拒绝，因此客户端增加了 token 文件回退机制：

```text
环境变量优先
  -> 环境变量不存在时读取 ~/.video-flow/token
```

该机制适合同事通过 Comfy Desktop 使用，不要求他们配置宿主进程环境变量。

## 四、缺口一：ExecutionAttempt 时间和 model 没有完整写入

### 4.1 当前现状

Prisma Schema 已经定义：

- `model`
- `submitted_at`
- `started_at`
- `finished_at`

但主执行链路没有完整写入这些字段。

Attempt 在 claim 阶段创建时，目前只写入：

- `taskId`
- `attemptNo`
- `mode`
- `provider`
- `status='pending'`
- `costStatus='unavailable'`

没有写入实际模型。

Backend 的通用状态更新已经能够接收 `startedAt` 和 `finishedAt`，但 Worker 的 `update_job_status()` 没有发送这两个字段。

`ExecutionsService.recordProviderSubmission()` 可以写入 `providerTaskId + submittedAt`，但 Worker 主链路没有调用该专用接口，而是使用通用 Task 状态 PATCH，因此 `submitted_at` 仍为空。

### 4.2 恢复超时字段还有映射错误

Backend 返回的是：

```text
attemptSubmittedAt
```

Worker 模型同时定义了：

```text
attemptSubmittedAt
submittedAt
```

但 Worker 在恢复和超时判断时读取的是：

```text
job.submittedAt
```

因此，即使数据库中的 `execution_attempts.submitted_at` 被补写，如果不修正字段映射，`is_stale_job()` 仍可能拿不到时间，运行超时保护不会生效。

### 4.3 测试存在假阳性

当前 claim 单元测试的 mock 会手工返回一个非空 `submittedAt`，但被断言的 `executionAttempt.create()` 请求本身没有写 `submittedAt`。

所以 Backend、Worker 测试全部通过，只能证明现有测试覆盖的回归行为通过，不能证明这几个字段在真实主链路中已经落库。

### 4.4 推荐的字段语义

建议统一为：

| 字段 | 推荐语义 |
|---|---|
| `startedAt` | Worker 开始处理本次 Attempt 的时间 |
| `submittedAt` | Provider 返回 `providerTaskId` 且该 ID 成功持久化的时间 |
| `finishedAt` | Attempt 进入终态的时间 |
| `model` | 实际提交给 Provider 的 effective model |

Attempt 终态至少包括：

- `completed`
- `failed`
- `cancelled`
- `requires_review`

### 4.5 不能破坏 Provider 提交不确定窗口保护

当前 Worker 在真正调用 Provider 前，会先把 Attempt 标成已进入提交阶段。如果 Provider 已接受任务但 Worker 没来得及保存 Provider Task ID，系统会进入 `requires_review`，避免自动重投造成二次计费。

补时间字段时必须保留这个安全不变量：

```text
Provider 请求结果不确定
  -> 不得自动创建第二个付费任务
  -> 必须进入 requires_review
```

推荐的最小流程：

```text
Worker 开始处理
  -> 写 startedAt 和 effective model
  -> 标记进入 Provider 提交阶段
  -> 调用 Provider
  -> Provider 返回 task ID
  -> 原子写 providerTaskId + submittedAt
  -> 轮询
  -> 终态写 finishedAt
```

## 五、缺口二：输入素材没有上传完成确认

### 5.1 当前链路

```text
Backend 创建 Asset，inspection_status='pending_upload'
  -> 返回 OSS 预签名 PUT URL
  -> 客户端 PUT 文件到 OSS
  -> 客户端直接使用 asset_id 创建 Task
```

PUT 完成后，客户端没有通知 Backend，Backend 也没有主动执行 OSS HEAD 验证。

### 5.2 直接后果

1. `inspection_status` 上传成功后仍是 `pending_upload`。
2. 输入 Asset 的 `bucket` 为空。
3. Backend 无法确认 OSS 对象是否真实存在。
4. Backend 无法确认对象大小、MIME 和客户端声明是否一致。
5. 拿到票据但上传失败的 Asset 仍可能被用于创建 Task。
6. 问题会延迟到 Worker 下载或 Provider 读取素材时才暴露。

### 5.3 推荐的最小修复

新增上传完成确认接口，例如：

```text
POST /api/v1/assets/:id/complete
```

该接口应完成：

- 校验 Asset 属于当前 actor。
- 对 OSS 执行 `HEAD object`。
- 校验对象存在。
- 校验实际 `sizeBytes`。
- 校验 Content-Type。
- 写入实际 `bucket`。
- 将状态从 `pending_upload` 更新为 `uploaded` 或 `verified`。

Worker 的输入 Asset 解析接口只允许状态为 `uploaded/verified` 的素材进入 Provider 调用。

### 5.4 SHA-256 的可信边界

当前 SHA-256 由客户端计算并提交。它可以用于客户端幂等和去重候选，但不能单独视为服务端已经验证文件内容。

推荐在预签名 PUT 中写入 OSS metadata：

```text
x-oss-meta-sha256: <digest>
```

完成确认时通过 HEAD 读取并核对该 metadata。

如果需要更强的内容校验，可以由服务端下载并重新计算 SHA-256，但对于较大素材会增加 Backend 带宽和计算开销，不建议作为所有上传的默认路径。

### 5.5 bucket 必须真实落库

当前签名服务隐式使用环境变量中的当前 bucket，输入 Asset 自己没有保存 bucket。

如果以后更换 bucket 或引入多 bucket，历史 Asset 可能会被错误地到新 bucket 中查找。因此即使当前只有一个 bucket，也应该在上传票据创建或完成确认时写入实际 bucket。

## 六、相关缺口：hash 去重没有数据库并发约束

当前服务端流程是：

```text
findByOwnerHash()
  -> 未找到
  -> create Asset
```

这是应用层“先查后建”，没有数据库唯一约束。两个并发请求可能同时查到不存在，然后分别创建两条 Asset。

所以连续串行执行两次复用成功，证明的是普通重复场景通过，不能证明并发幂等已经闭合。

建议最终增加数据库唯一约束：

```text
UNIQUE(owner_id, role, file_hash)
```

创建 Asset 时捕获唯一冲突，再回读既有记录。

## 七、缺口三：历史 file_hash 回填

### 7.1 风险判断

旧输入素材没有 `file_hash` 不会阻断新任务，但会导致：

- 相同历史素材再次上传时无法复用旧 Asset。
- 无法准确判断历史素材是否相同。
- 无法在增加数据库唯一约束前识别历史重复数据。

该问题优先级低于上传完成确认和 Attempt 追溯，但应在唯一约束上线前处理。

### 7.2 推荐先做只读 dry-run

报告至少包含：

- 输入 Asset 总数。
- `file_hash IS NULL` 数量。
- OSS 对象存在数量。
- OSS 对象缺失数量。
- 可成功计算 SHA-256 的数量。
- 同一 owner 下重复 SHA-256 分组。
- 预计更新行数。
- 无法处理的 Asset ID 和原因。

### 7.3 回填原则

- 只对 OSS 对象真实存在且下载成功的记录计算 SHA-256。
- 第一轮只回填 hash，不自动删除或合并重复 Asset。
- 不要直接修改历史 Task 的 `request_snapshot`。
- 对重复记录先形成报告，再决定是否迁移引用关系。
- 完成重复数据处理后再增加唯一约束。

不能只用文件名和大小判断相同文件；必须对真实对象内容计算完整 SHA-256。

## 八、费用口径分析

当前 `¥7.623` 来自代码公式：

```text
total_tokens × ¥70 / 1,000,000
```

这只能证明：

```text
Provider usage × 本地配置价格 = ¥7.623
```

不能证明火山最终账单一定扣除 `¥7.623`。

费用必须分为三层：

| 层级 | 含义 |
|---|---|
| `estimated` | 调用前估算 |
| `usage_calculated` | 根据 Provider usage 和本地价格配置计算 |
| `billed` | 已与火山账单明细核对 |

当前任务只能标为：

> 本次 usage-derived cost 为 ¥7.623，账单金额待火山费用中心核对。

项目原先的 `¥2-5` 应标为早期估算。不能根据一个样本立即把 `¥7.623` 固化为每条视频的预算。

账单核对时至少检查：

- 调用发生时间。
- 模型和具体计费项。
- usage 数量。
- 原价。
- 账号折扣或资源包抵扣。
- 实际应付金额。
- 同一时间附近是否存在其他 Provider 调用。

官方参考：

- [火山引擎费用中心账单管理](https://www.volcengine.com/docs/6269/94009)
- [收支明细与账单的区别](https://www.volcengine.com/docs/6269/100447?lang=zh)

## 十、风险与优先级

| 优先级 | 项目 | 主要风险 |
|---|---|---|
| P1 | Asset 上传完成确认、bucket、OSS HEAD | 数据库存在虚假素材记录，失败延迟到 Provider 阶段 |
| P1 | Attempt model 和时间链 | 无法完整审计，恢复超时逻辑可能失效 |
| P1 | hash 数据库唯一约束 | 并发上传仍可能产生重复 Asset |
| P1 | Production 凭证撤销 | 验收 token 长期留存扩大凭证风险 |
| P1 | 火山账单核对 | usage 推算价格可能与实际账单不一致 |
| P2 | 历史 `file_hash` 回填 | 历史素材无法复用和去重 |

## 十一、推荐实施顺序

1. 先整理并提交当前已经完成真实验收的 Preview、Production 和幂等修复，避免继续叠加在未提交工作区。
2. 修复 Attempt：effective model、`startedAt`、`submittedAt`、`finishedAt`、恢复字段映射。
3. 修复 Asset：上传完成确认、OSS HEAD、bucket 落库、未完成 Asset 禁止进入执行链路。
4. 增加 Asset hash 并发唯一约束；上线前先处理可能的历史重复。
5. 生成历史 Asset hash 回填 dry-run 报告。
6. 审核报告后执行回填，不自动合并或删除历史记录。
7. 拉取火山账单，将本次费用从 `usage_calculated` 核对为 `billed`，保留两个数值而不是覆盖。
8. 撤销 paid actor credential，清理临时明文凭证副本。

## 十五、2026-09-10 实施结果

本轮已在当前工作区完成以下修改：

- Attempt 状态回写支持 actual/effective model。
- Worker 开始执行时写 `startedAt`。
- Provider Task ID 持久化时写 `submittedAt`。
- Attempt 进入完成、失败或人工复核路径时写 `finishedAt`。
- Worker 恢复逻辑优先使用 `attemptSubmittedAt`，兼容旧 `submittedAt`。
- 补齐 Worker 遗漏的 `failureType` 回写。
- 输入素材预签名 PUT 携带 `x-oss-meta-sha256`。
- 新增 `POST /api/v1/assets/:id/complete`。
- Backend 使用 OSS HEAD 核对 size、MIME 和 SHA-256 metadata。
- 上传确认后写入 bucket，并将 `inspectionStatus` 更新为 `uploaded`。
- 未确认的输入 Asset 不再生成公共或 Worker 下载签名。
- 已上传的 canonical Asset 不再签发重复 PUT，避免覆盖原对象。
- 增加 `(ownerId, role, fileHash)` 数据库唯一约束，并处理并发 `P2002` 回读。
- 增加历史 Asset hash dry-run/apply 工具。

历史工具使用方式：

```bash
cd packages/backend
npm run build

# 只读盘点，默认模式
npm run assets:backfill

# 明确审核 dry-run 报告后才允许执行
npm run assets:backfill -- --apply
```

工具只扫描需要补齐 hash 或上传状态的 input Asset。`--apply` 只更新能够从 OSS 成功读取并计算 SHA-256 的记录，不删除、不合并 Asset，也不改写 Task 历史快照。
