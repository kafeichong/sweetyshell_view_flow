最合适的方案不是给每位同事配置火山引擎密钥，也不是在服务器上再部署一套 ComfyUI，而是：

  同事电脑
  ComfyUI + 公司自定义节点 + 本地模型
                  │
                  │ HTTPS + 个人/设备凭证
                  ▼
  公司统一 Backend
  鉴权 / 上传 / 任务 / 限额 / 记录
                  │
                  ▼
  服务器 Worker
  统一持有火山和 OSS 密钥
                  │
           ┌──────┴──────┐
           ▼             ▼
  火山 Seedance        阿里云 OSS

  这样同时满足：

  - ComfyUI 和本地模型继续留在同事各自电脑上。
  - Seedance 全部走公司已经充值的火山引擎账号。
  - 同事不需要安装 Seedance 模型，也不接触 Ark/OSS 密钥。
  - ComfyUI 仍然是创意工作流界面，可以调 Prompt、时长、画幅、参考图等参数。
  - 所有付费生成统一经过服务器，天然可以增加人员、任务、失败、费用、限额和审计功能。
  - 同事自己的本地模型工作流不会受到影响，本地节点生成的图片也可以继续上传给 Seedance。

  我在 2026-09-10 只读检查了实际服务器。当前 /data/video-flow 的 PostgreSQL、Backend、Worker 三个
  容器都在运行，生产 Worker 明确配置为 COMFYUI_ENABLED=false，实际生成链路已经是“服务器 Worker 直
  接调用 Seedance”，这个基础方向是正确的。

  ## 当前代码已经具备什么

  - NestJS Backend 提供任务创建、查询、更新接口。
  - PostgreSQL 保存基础任务状态。
  - Python Worker 轮询 pending 任务。

  - 已经部署到公司服务器并真实生成过视频。

  - packages/backend/src/tasks/tasks.controller.ts

  - packages/worker/providers/seedance_adapter.py:30

  ## 当前系统还不能直接给同事使用的原因

  ### 1. 没有真正的身份和鉴权

  当前创建任务时，createdBy 是客户端自行提交的字符串。任何人都可以写成“张三”或“管理员”，不能作为费
  用归属依据。

  Backend 的任务创建、查询和更新接口没有鉴权。只要能访问端口，就可能：

  - 创建付费任务。
  - 查看其他人的任务。
  - 修改任务状态。
  - 伪造使用人。
  - 恶意消耗公司火山余额。

  正确做法是给每位同事签发独立、可撤销的凭证，createdBy/userId 必须由服务器从凭证中确定，不能由
  ComfyUI 自己提交。

  ### 2. 服务器端口暴露边界不合理

  当前 Compose 把以下端口绑定到主机所有网卡：

  - Backend：3100
  - Worker：8101
  - PostgreSQL：5433

  这不等于已经确认能从公网访问，因为还可能有云防火墙限制，但从部署文件看，应用没有形成安全边界。

  推荐调整为：

  - 只对外开放 HTTPS 443。
  - Nginx/Caddy 反向代理 Backend。
  - Worker 不开放主机端口，只在 Docker 网络中运行。
  - PostgreSQL 不开放主机端口，或至少限制为本机/运维白名单。
  - ComfyUI 节点只能访问 HTTPS Backend，不能访问 Worker、数据库和 Ark。

  ### 3. Worker 写了恢复逻辑，但关键字段没有落库

  Worker 已经接收这些参数：

  - provider_task_id
  - provider_usage
  - pricing_version
  - cost_status
  - failure_type

  但 packages/worker/executor.py:125 的实际更新 payload 只保留：

  - status
  - cost
  - videoUrl
  - errorMsg
  - completedAt

  数据库 packages/backend/prisma/schema.prisma 也没有 providerTaskId 等字段。

  后果是：

  - 火山已经接受任务后，如果 Worker 重启，系统无法可靠恢复原任务。
  - 最危险的窗口是“火山创建成功，但 provider task ID 尚未持久化”，重启后可能重复提交并再次计费。
  - 无法保存火山原始 usage。
  - 无法判断费用是估算、usage 计算还是账单确认。
  - 失败分类和重试次数不能可靠保存。

  这是接入多位同事前必须先修的执行完整性问题。

  ### 4. 多 Worker 会产生重复付费风险

  当前 Worker 是“查询 pending 列表后执行”，没有数据库原子抢占或任务租约。

  部署总结中提到未来可以横向扩展 Worker，但按当前实现直接扩容是不安全的：两个 Worker 可能同时读取
  同一个 pending 任务，然后分别向火山提交一次。

  需要增加：

  - clientRequestId 幂等键。
  - 数据库原子 claim。
  - ExecutionAttempt 唯一执行记录。
  - Provider task ID 提交后立即持久化。
  - 不确定是否已提交时进入 requires_review，不能自动重新生成。

  ### 5. 本地图片还没有正式的统一上传入口

  同事在 ComfyUI 中选择的 /Users/.../product.png 只是本机路径，火山引擎无法读取。

  正确链路应是：

  ComfyUI 选择本地文件
      → Backend 申请上传凭证
      → 文件直传 OSS
      → Backend 保存 Asset/objectKey
      → Seedance 请求使用 Provider 可访问的 URL

  建议使用 OSS 预签名上传，不要让大图片和视频全部穿过 NestJS。

  当前 Worker 会调用 /api/assets 创建素材记录，但当前 Backend 中没有发现对应的 Assets 模块，调用失
  败后也只是打印错误，不会阻止任务完成。因此目前的视频回写成功不代表素材记录链路已经完成。

  ### 6. 当前 videoUrl 保存的是会过期的地址

  packages/worker/oss_uploader.py:19 返回的是有效期 7 天的签名 URL。

  把它直接保存成 Task.videoUrl 会导致：

  - 七天后数据库里的地址失效。
  - 历史任务无法播放。
  - 同事可能误以为文件被删除。

  应该永久保存：

  - bucket
  - objectKey
  - mimeType
  - size
  - fileHash

  用户需要查看或下载时，再由 Backend 生成新的短期签名 URL。

  ### 7. 当前费用只能算“usage 推算值”

  当前代码按固定的 ¥70 / 百万 tokens 计算费用，并把有 total_tokens 的记录称为 confirmed。

  这个命名不够严谨：

  - Provider 返回 usage，只能证明“有使用量”。
  - 按配置价格计算出来的是 usage-derived cost。
  - 真正的账单确认需要和火山账单或结算数据对账。

  建议将费用状态改为：

  estimated          提交前估算
  usage_calculated   根据 Provider usage 计算
  billed             已与火山账单对账
  unavailable        Provider 未提供足够数据

  费用字段建议使用数据库 Decimal/Numeric，不要继续用 Float。当前价格和模型支持范围也应在实施前重新
  核对火山官方配置，不能把代码中的默认模型名和反推价格当作长期有效事实。

  ## 推荐的 ComfyUI 接入方式

  新增一个轻量的公司内部插件，例如：

  ComfyUI-Video-Flow-Client

  插件只负责客户端交互，不包含公司 Ark 和 OSS 密钥。

  建议第一版提供以下节点：

  - VideoFlow Config：配置服务器地址和个人凭证，一次配置即可。
  - VideoFlow Upload Media：把本地图片、视频上传到统一素材入口。
  - VideoFlow Seedance Generate：提交 Prompt、模型、时长、比例、参考素材等参数。
  - VideoFlow Wait Task：轮询服务器任务状态。
  - VideoFlow Load Result：下载或加载生成结果到 ComfyUI。

  也可以把后四个节点封装成一个更简单的组合节点，让普通同事只看到：

  图片 + Prompt + 时长 + 比例
               ↓
        Company Seedance
               ↓
             视频

  节点内部执行：

  1. 读取个人/设备凭证。
  2. 上传本地素材。
  3. 生成 clientRequestId。
  4. 向 Backend 创建任务。
  5. 轮询任务状态。
  6. 下载生成视频。
  7. 把结果输出给后续 ComfyUI 节点。

  同事安装时只需要：

  1. 安装 ComfyUI。
  2. 安装公司节点包。
  3. 填一次服务器地址和个人凭证。
  4. 导入公司提供的 Workflow。

  不需要：

  - 安装 Seedance 模型。
  - 配置火山 API Key。
  - 配置 OSS Key。
  - 安装服务器 Worker。
  - 连接公司数据库。

  ## 服务端建议的数据边界

  不要继续只在当前 Task 表上不断堆字段。最低限度应区分“用户想做什么”和“真正产生费用的一次调用”。

  ### User / ApiCredential

  保存：

  - 使用人。
  - 部门。
  - 凭证哈希。
  - 是否启用。
  - 单日/月限额。
  - 最后使用时间。
  - 可用 Provider/模型范围。

  Ark Key 不放这里。Ark Key 仍由服务器环境变量或后续 Secret Manager 管理。

  ### Task

  代表用户意图，保存：

  - 用户和设备。
  - clientRequestId。
  - Prompt。
  - capability。
  - generation 参数。
  - Workflow 名称、版本、hash。
  - 输入 Asset。
  - 当前总体状态。
  - 创建和完成时间。

  ### ExecutionAttempt

  代表一次可能收费的执行，保存：

  - Task ID。
  - Provider 和模型。
  - Provider task ID。
  - 请求快照。
  - Provider 状态。
  - 原始 usage。
  - 费用状态。
  - 估算费用、usage 计算费用、账单费用。
  - pricing version。
  - failure type/code/message。
  - submitted/started/finished 时间。
  - 是否人工重试。

  “重新生成”必须新建一个 Attempt，不能覆盖原执行记录。

  ### Asset

  保存：

  - 输入或输出类型。
  - OSS bucket/objectKey。
  - MIME、大小、hash。
  - 上传者。
  - 来源 Task/Attempt。
  - 内容检测状态。
  - 创建时间。

  ### TaskEvent

  可以后置，但未来做检测和排障时很有价值：

  - created
  - media_uploaded
  - claimed
  - provider_submitted
  - provider_running
  - provider_succeeded
  - output_archived
  - failed
  - manually_retried

  第一版不一定要单独建 Event 表，也可以先使用结构化日志；但 ExecutionAttempt 不能省略。

  ## 分阶段实施建议

  ### 第一阶段：先修服务端底座

  这是正式开放给同事前的必要条件：

  - 增加 Backend 鉴权。
  - 每位同事独立可撤销凭证。
  - 关闭 Worker/PostgreSQL 对外端口。
  - Backend 通过 HTTPS 提供服务。
  - 增加 Task + ExecutionAttempt + Asset 基础结构。
  - 持久化 Provider task ID、usage、失败分类和时间。
  - 增加幂等键和任务原子 claim。
  - 保存 OSS objectKey，不再把签名 URL 当永久地址。
  - 增加输入素材预签名上传。
  - 增加请求参数 DTO 校验和服务端允许值校验。

  ### 第二阶段：让同事在 ComfyUI 中使用

  - 开发公司 ComfyUI 客户端节点。
  - 输出一个受控的 Seedance Workflow。
  - 节点只连接公司 HTTPS API。
  - 支持上传、提交、轮询、下载。
  - 用户和设备自动归属。
  - 保留本地模型节点，可将本地生成结果继续送给云端 Seedance。

  这一阶段完成后，你提出的前 3 项要求就基本实现了。

  ### 第三阶段：检测、记录和费用

  - Provider/Worker/OSS 健康检查。
  - 失败类型和错误码统计。
  - 内容安全检测结果保存。
  - 按人、部门、模型、Workflow 统计用量。
  - 单人日限额、月限额。
  - 超额提醒或审批。
  - usage 费用与火山账单对账。
  - Workflow 版本管理。
  - 任务搜索、下载和历史回放。
  - 管理后台。

  ## 第一阶段验收标准

  满足以下条件才适合推广给同事：

  - 同事电脑里不存在公司 Ark/OSS 密钥。
  - 撤销某位同事的凭证不会影响其他人。
  - 同一 clientRequestId 重复提交不会产生第二次付费任务。
  - Worker 重启后能通过 Provider task ID 恢复轮询。
  - 多个 Worker 不会领取同一个任务。
  - 所有输入素材都能转换成 Provider 可访问地址。
  - 历史视频签名 URL 过期后可以重新生成。
  - 每次调用都能追溯到用户、设备、Workflow、Provider 和 Attempt。
  - usage 缺失时显示“未知”，不能显示成零元。
  - Worker 和 PostgreSQL 不直接暴露给同事电脑。
  - 同事原有本地模型与工作流不受影响。

  ## 一个需要你决定的核心问题

  问题：同事是否可以不经过审批，直接产生火山引擎付费任务？

  **推荐：**允许直接生成，但必须设置个人日/月额度，提交前显示费用估算；超过额度或使用高成本模型时
  才进入审批。

  **原因：**每次都审批会破坏 ComfyUI 调参效率，但完全无限制又无法控制共享账户风险。

  **主要代价：**需要第一阶段就建立用户身份、额度和可靠的费用记录。

  **备选：**所有 Production 任务都必须由管理员批准。

  **适合备选的情况：**当前充值金额较小、素材合规风险较高，或者同事还处于试用阶段。

  Provider 费用。
