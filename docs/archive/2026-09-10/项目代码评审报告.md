## 一、结论摘要

当前代码骨架方向正确：`Task` / `ExecutionAttempt` / `Asset` / `ActorCredential` 的数据模型、v1 鉴权入口、原子 claim、Provider 提交前持久化、`requires_review` 人工介入分支等关键设计都已经落地，属于高质量的设计意图。

但**现状不可上线**，原因是三条主链路在同一条流水线上互相不匹配：

1. **唯一带鉴权的业务入口（v1）创建出来的任务，Worker 永远不会领取。**
2. **参考图（image_asset_id）在 v1 → Backend → Worker 的传递中断裂，图生视频会静默退化成文生视频。**
3. **Worker 每轮轮询都会把刚 claim 到的任务立即改写成 failed，恢复机制自我否定。**

外加一个硬阻断：**Prisma 迁移缺列，用 `prisma migrate deploy` 建库后 `execution_attempts` 查询会直接报表不存在**。

实机验证结果：

## 二、P0 阻断级问题（必须先修，否则功能不成立/有资金风险）

### P0-1 v1 创建的任务永远不会被 Worker 领取

- 写入端：`packages/backend/src/tasks/tasks.service.ts:67` `createV1()` 写入 `taskStatus: 'pending'`
- 读取端：`packages/backend/src/tasks/task-claim.service.ts:18` `claimNext()` 的筛选条件是 `taskStatus: null`

两者严格互斥。`packages/backend/src/tasks/task-claim.service.spec.ts:60-66` 甚至把 `taskStatus: null` 这个条件用测试锁死了，说明该不一致已被"固化"。

影响：ComfyUI 客户端是唯一走 v1 的入口（`packages/comfyui-video-flow-client/client.py:38`），也就是**公司主推的接入方式提交的所有任务都会永久停在 pending，Worker 一条都拿不到**；而 `TaskClaimService.claimNext` 的 3 次重试也永远拿不到候选。

建议：`createV1` 写入 `taskStatus: null`（或 `'queued'`），并把 claim 条件改为"可领取状态集合"而非 `null` 哨兵；同时补一条端到端测试（v1 创建 → claim 能取到）。

### P0-2 参考图在 v1 → Worker 链路上丢失，图生视频静默退化为文生视频

链路逐段断开：

1. ComfyUI 节点提交 `params: {prompt, image_asset_id}`：`packages/comfyui-video-flow-client/nodes.py:43`
2. Backend 只挑出 `params.image_url` 存成 `Task.imageUrl`，`image_asset_id` 只留在 `requestSnapshot` 里：`packages/backend/src/v1/tasks/v1-tasks.controller.ts:51-52`
3. Worker 的 `Job` 模型没有 `requestSnapshot` 字段（`packages/worker/models.py:28-71`），解析时被丢弃
4. `Job.get_params()` 只用 `prompt` + `imageUrl` 重建参数：`packages/worker/models.py:73-85`，因此 `params` 里没有 `image_asset_id`
5. `executor.py:394` 的 `provider_params.get("image_asset_id")` 恒为 `None`，`resolve_asset_url()` 从不被调用

结果：Worker 用默认 `ratio=16:9 / duration=5 / model=doubao-seedance-2-5-260628` 发一个只有文本的 Ark 请求（`seedance_adapter.py:97-104`），**用户上传的参考图被完全忽略且没有任何报错**。同理，v1 `params` 里的 `ratio`、`duration`、`seed`、`negative` 等参数也全部被丢弃。

建议：把 `requestSnapshot`（或显式的 `params`）完整传给 Worker，由 Worker 用 `params` 走 `get_params()`；并补一条"v1 提交 image_asset_id → Ark payload 含 image_url"的契约测试。

### P0-3 Worker 每轮都把刚 claim 的任务改写成 failed，恢复逻辑自我否定

调用时序（`packages/worker/executor.py:641-651`）：

```
jobs  = await fetch_pending_jobs()      # claim：status=submitted, taskStatus=in_progress, attempt.status=pending
jobs += await fetch_inflight_jobs()     # 紧接着 GET /api/tasks/recover
```

- `findRecoverable()` 的条件是 `taskStatus='in_progress' AND status IN ('submitted','running')`（`task-claim.service.ts:74-89`）——**刚 claim 的任务完全命中**
- `fetch_inflight_jobs()` 中，`should_resume_job()` 因为还没有 `provider_task_id` 而返回 false
- 随后的保护分支要求 `job.attemptStatus == "submitted"`（`executor.py:125-129`），但 claim 刚创建 attempt 时状态是 `'pending'`（`task-claim.service.ts:58`），条件不成立
- 于是落入 `executor.py:152-157`，把任务直接 `FAILED` + `task_status='failed'` + `completedAt`

影响：
- 每个任务在"正在执行"的同时，数据库里已被标记为 failed；
- 若 Worker 在这之后崩溃，任务永久停留在 failed 且不再被 recover 拾取，而 Ark 侧可能已受理并计费 → **产生无人对账的付费孤儿任务**；
- `completedAt` 被错误地提前写入。

建议：claim 后 attempt 直接置为 `submitted`（或让恢复筛选排除"尚未提交"的 attempt），并让 `findRecoverable` 只返回 `attemptStatus IN ('submitted','running')` 的记录；`fetch_pending_jobs` 与 `fetch_inflight_jobs` 的结果需要按 task id 去重。

### P0-4 Prisma 迁移缺列，按迁移建库后执行链路直接报错

`packages/backend/prisma/schema.prisma:106` 定义了 `model String?`，但迁移 `packages/backend/prisma/migrations/20260910_expand_execution_domain/migration.sql` 的 `CREATE TABLE execution_attempts` 中**没有 `model` 列**（已用 `grep -rn '"model"' migrations/` 确认为 NOT FOUND）。

Prisma 默认 `SELECT` 会带出所有标量字段，因此用 `prisma migrate deploy` 建库后，任何 `executionAttempt` 查询/写入都会报 `column ... does not exist`，claim 路径直接不可用。

同时存在两处迁移规范风险，建议一并核对：
- 迁移目录名 `20260910_expand_execution_domain` 不是 Prisma 标准的 `YYYYMMDDHHMMSS_name` 格式，`migrate deploy` 可能报无效迁移名；
- `@@unique([providerTaskId])` 在迁移里实现为**部分唯一索引**（`WHERE provider_task_id IS NOT NULL`），与 schema 声明不一致，`migrate diff` 会检测出漂移。

建议：用 `prisma migrate dev` 重新生成一份与 schema 对齐的迁移，并增加 CI 步骤执行 `prisma migrate diff --exit-code` 防止再次漂移。

### P0-5 `/api/tasks` 全部内部接口零鉴权

`packages/backend/src/tasks/tasks.controller.ts` 的 `create / findAll / findOne / findPending / claim / recover / update` 七个路由**没有任何 Guard**。`VIDEO_FLOW_WORKER_TOKEN` 只保护了 `/api/v1/internal/*`（`v1-worker.controller.ts:8`）。

`docker-compose.yml:39-40` 又把 3100 端口发布到主机所有网卡，因此任何能访问该端口的人都可以：
- 创建付费任务（`POST /api/tasks`）；
- 遍历全部任务与提示词（`GET /api/tasks`，且无分页）；
- 篡改任意任务的 `status / cost / attemptStatus / providerTaskId`（`PATCH /api/tasks/:id`）；
- 抢先 `claim` 任务。

这正是 `docs/2026-09-10/当前代码已经具备什么.md:63-69` 已经指出的问题，v1 修好了，旧接口没修。

建议：至少给 `claim / recover / update` 加 `WorkerServiceGuard`，把 `create / findAll / findOne / findPending` 下线或加 actor 鉴权；Compose 中把 3100 收敛到 127.0.0.1 交由反代暴露。

### P0-6 生成的视频地址从未落库，Asset 记录也写不进去

- `executor.py:449-460` 完成 OSS 上传后，`uploaded_video_url` 被赋值，但后续 `update_job_status()`（`executor.py:474-483`）**没有任何一个 payload 带 `videoUrl`**；该变量随后被丢弃（死变量，`executor.py:345/450`）。因此 `Task.video_url` 永远是 `NULL`。
- `create_asset()` POST 到 `/api/assets`（`executor.py:286`），但后端**没有注册这个路由**（`@Controller` 只有 `tasks`、`v1/tasks`、`v1/assets`、`v1/internal/attempts` 四组），失败只在 `executor.py:290-291` 打印一行日志。
- 仓库里存在 `backfill_video_urls.py` 且硬编码两个生产 task id，正是这一环缺失的补丁痕迹。

另外 `oss_uploader.py:23` 返回的是 **7 天有效的签名 URL**，把它当永久地址保存本身也是错的（`当前代码已经具备什么.md:154-172` 已指出）。正确做法是持久化 `bucket + objectKey + mime + size + hash`，展示时再签短链。

建议：补齐 Assets 写入路由（或让 Worker 走 `PATCH /api/v1/internal/attempts/:id/...` 的既有内部接口），把 `videoUrl` 改为 `objectKey`，并在完成更新中显式回写。

## 三、P1 高优先级问题

### P1-1 重试逻辑是死代码，可重试失败一律变成永久失败

`executor.py:521-535` 的重试 PATCH 发送的是 **snake_case**：`failure_type / retry_count / next_retry_at`，而后端 `tasksService.update()` 只认识 camelCase，且会把这些字段整个展开进 Prisma `data`（`tasks.service.ts:127-140`）。Prisma 对未知参数抛 `PrismaClientValidationError` → 500。

更根本的是 **schema 里根本没有 `retry_count` / `next_retry_at` 字段**（已 grep 确认）。所以：
- 重试请求 500，Worker 打印 "Failed to schedule retry"；
- 任务停留在 submitted/running，下一轮被 `fetch_inflight_jobs` 判为 failed（见 P0-3）；
- `Job.retryCount / maxRetries` 也从不由后端下发，恒为 0/3。

`worker/README.md:70` 仍把"实现重试逻辑"列为 TODO，与实际代码的乐观注释不符。

### P1-2 v1 幂等实现有竞态，且 JSON 比较会误判 409

`v1-tasks.controller.ts:31-53`：

- **check-then-act 竞态**：并发同 key 请求会双双通过 `findByActorRequest`，随后 `create` 触发 `@@unique([actorId, clientRequestId])` 的 P2002，返回 500 而不是既有任务；未捕获 P2002。
- **JSON 比较不可靠**：`JSON.stringify(existing.requestSnapshot) === JSON.stringify(body)`。`requestSnapshot` 存入的是 PostgreSQL `jsonb`，jsonb 会规范化键顺序并去重，而 `body` 保持请求的键顺序。同一 payload 只要键序不同就会误判为"不同 payload"并返回 409。

建议：入库时额外存 `requestHash`（对规范化 JSON 做 SHA-256），比较哈希；并 catch P2002 回读返回。

### P1-3 `providerProfile` 字段不存在，provider/model 路由实际失效

`task-claim.service.ts:57/120` 读取 `candidate.providerProfile`，但 `Task` 模型没有该字段（已 grep：仅出现在该 service 与其 spec 中）。因为事务回调参数是 `any`，`npm run build` 能通过，运行时静默得到 `undefined` → `normalizeProvider()` 恒返回 `'seedance'`。

后果：`workflowName`（v1 的 `profile`）与 provider/model 选择完全脱节，`providers/capabilities.py` 里精心维护的模型能力矩阵（含 MiniMax-H3）没有任何调用方。

### P1-4 素材签名服务没有部署，资产链路整体 503

- `AssetPresignService` 读取 `OSS_PRESIGN_ENDPOINT`，未配置即抛 503（`asset-presign.service.ts:6-9`）；
- `.env.example:14` 文档化了该变量，但 `docker-compose.yml` 的 `video-backend` 环境变量里**没有传递它**（已确认）；
- 仓库与 Compose 中都不存在 `oss-signer` 这个服务实现。

因此 `POST /api/v1/assets/upload-ticket`、`GET /api/v1/assets/:id/download`、以及 Worker 的 `resolve_asset_url()` 在生产部署下全部 503，参考图上传链路不可用（客户端 README 把 503 描述为"预期的安全失败"，但它是唯一路径，不是降级路径）。

### P1-5 鉴权/Actor 归属未真正落地到计费

- `ActorCredential` 有 `dailyLimitCny / monthlyLimitCny`，但**没有任何限额校验代码**（已 grep：仅 schema 定义）；
- v1 创建任务不写 `workflowVersion / workflowHash`（schema 已预留）；
- `CreateTaskDto` 是无校验的普通 class（`create-task.dto.ts`），`main.ts` 也没有全局 `ValidationPipe`，`capability / profile / params` 全不校验；
- v1 完全忽略 `body.mode`（`v1-tasks.controller.ts`），客户端传 `mode:'production'` 与 `preview` 行为一致 —— README 声称的"Production 入口尚未开放"在服务端**没有强制**。

### P1-6 Worker 恢复隔离区只存在内存里

`executor.py:55-57` 的 `_comfyui_quarantined_job_ids` / `_comfyui_manual_intervention_job_ids` 是实例级 `set`，重启即丢失；`_record_comfyui_submission` 的注释声称"确保进程重启后有稳定恢复锚点"，但隔离状态本身没有持久化，重启后可能重放已提交的 ComfyUI prompt。

## 五、做得好的部分（应保留）

- 数据模型方向正确：`Task`（用户意图）与 `ExecutionAttempt`（一次可能计费的执行）分离，`providerUsage / costStatus / estimated·usage_calculated·billed` 三档费用字段齐全，具备后续对账基础。
- 费用语义克制：`format_cost()` 对未知费用返回 `unknown` 而非 `¥0.00`（`recovery.py:7-10`），dry-run 显式返回 `unavailable`（`comfyui_status.py:52-60`），避免了"未知当零元"的财务误判。
- 提交不确定性处理：`ProviderSubmissionUncertainError`（`seedance_adapter.py:11`）与 `SUBMISSION_UNCERTAIN → requires_review` 分支（`executor.py:494-506`）是防重复计费的正确设计。
- `claimNext` 用 `updateMany` + 条件 where 做乐观并发控制（`task-claim.service.ts:27-44`），思路正确。
- v1 凭证采用 `sha256(token)` 存储、`timingSafeEqual` 比较 Worker token（`credentials.service.ts:9-11`、`worker-service.guard.ts:15-16`），基础安全实践到位。
- `WorkerServiceGuard` 的常量时间比较与"未配置即失败"（fail-closed）是正确的默认。
- ComfyUI 输出路径做了 `relative_to(output_dir)` 逃逸校验（`comfyui_executor.py:132-138`），API 格式工作流做了严格的安全链路校验（`comfyui_workflow.py:180-244`）。
- 密钥未入库、未入仓：`.env` 已被 gitignore，`.env.example` 全是占位符，对已跟踪文件的正则扫描未发现真实密钥。
